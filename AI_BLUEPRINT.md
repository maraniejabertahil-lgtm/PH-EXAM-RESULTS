## Purpose and Scope

This SOP defines how to handle a hard blocker during implementation, such as a restrictive API, missing documentation, or a performance limit. It replaces open-ended brute-force debugging with a time-boxed, structured path from engineering workaround to formal escalation.

**What counts as a hard blocker.** Progress on a required outcome has stopped and the time-box in Part 1, Step 0 has been reached. Examples:

* An API does not expose a field the feature depends on, or enforces undocumented rate limits.
* Latency, timeout thresholds, or throughput caps make the approved architecture non-viable.
* A library or platform cannot do something the specification requires, and the documentation is silent or contradictory.

## Part 1: Constraint Resolution Protocol

### Step 0. Time-Box and Sanity Check

Before designing any workaround:

* **Set the trigger.** Start this protocol after **2 hours** of unproductive debugging or **3 failed approaches**, whichever comes first. Adjust the numbers to the task's size and urgency.
* **Check the basics:** official docs, changelogs, release notes, known issues, community threads, and the vendor's support channel.
* **Ask a colleague.** A fresh pair of eyes often dissolves the blocker.
* **Notify stakeholders.** Send a short heads-up using the format below. This is not an escalation, only visibility.
* **If the blocker is resolved at this step,** stop, and log the cause and fix.

**Blocker notification format:**

```text
[BLOCKER ALERT] Feature/Module: <Module Name>
- Desired Outcome: <Target Result>
- Blocker Description: <Specific Error / Limit>
- Time Spent: <e.g., 2 hours / 3 failed approaches>
- Methods Attempted:
  1. <Attempt 1>
  2. <Attempt 2>
  3. <Attempt 3>
- Current Status: Step 0 triggered. Entering Constraint Resolution Protocol.
- Primary Engineer: @<handle>
```

### Step 1. Deconstruct the Constraint (First Principles)

* **Shift focus.** Stop concentrating on the failing tool. Strip the problem down to its core objective.
* **Classify the boundary:**
  * **Hard limit:** physics, network latency, strict external rate limits, or limits set by policy, contract, or law (for example, the Data Privacy Act of 2012 (RA 10173) and current National Privacy Commission issuances, GDPR, or contractual obligations).
  * **Soft limit:** inflexible architecture, a suboptimal library, or local configuration.
* **Abstract the requirement.** Define the exact outcome needed without referencing the current technology stack.

> **Critical rule:** A hard limit set by policy, terms of service, or law is **not** a candidate for a bypass. Go directly to Part 2.

### Step 2. Component Recombination (Find the Adjacent Possible)

Identify alternative technologies or methods that achieve the same outcome through different mechanics.

* **Example paths:**
  * Direct database query fails -> evaluate an API endpoint.
  * API endpoint fails or is blocked -> evaluate an official export, a partner integration, or a vendor-supported alternative **before** considering scraping or OCR.
* **Compliance gate (mandatory).** Confirm each candidate respects the platform's terms of service, licensing, security policy, and data-privacy requirements. Do not circumvent authentication, access controls, or rate limits. If unsure, consult legal, security, or the platform owner, and record who approved and when.
* **Evaluate each candidate on:**
  * Reliability
  * Maintainability and long-term technical debt
  * Cost (infrastructure, licensing, engineering time)
  * Data quality and accuracy
  * Compliance risk
* Select the path with the best overall balance, not only the highest reliability.
* **If no compliant alternative exists,** go to Part 2.

### Step 3. Bypass Engineering (Design the Fallback Loop)

Engineer a routing mechanism that fails gracefully instead of crashing the system.

**Cascading logic:**

1. Attempt the primary method.
2. On failure, trigger the alternative method.
3. On failure, output clean logs and flag for manual intervention.

**Required safeguards:**

* Retries with exponential backoff and a retry cap.
* A circuit breaker so a failing path is not hammered.
* Idempotent operations so retries never duplicate data or side effects.
* Alerting when the fallback activates or the manual-intervention path is reached.
* A **provenance tag** on all data from fallback sources (origin, method, timestamp, confidence), so downstream users know its source and quality.

### Step 4. Micro-Prototyping (Isolate and Test)

* Do not integrate the workaround directly into the primary codebase.
* Build a lightweight, isolated script that tests only the bypass mechanism.
* Define success criteria before testing.
* Verify under realistic edge conditions: malformed input, timeouts, rate limiting, partial failures, and realistic data volume.
* Record the results.
* **If the prototype fails the success criteria,** go to Part 2.

### Step 5. Integration and Hardening

* Merge the validated prototype into the main architecture.
* Wrap the bypass in strict error handling, telemetry, and structured logging.
* Keep all original validation rules, security checks, and data-integrity constraints active.
* Add automated tests covering both the primary path and the fallback path.

### Step 6. Document and Close the Loop (Architecture Decision Record)

* Record the decision: the constraint, the options considered, the option chosen, and why.
* Assign a **named owner** for the workaround.
* Set a **review date** to retire or revisit the workaround, and a trigger such as a vendor API update or a change in requirements.
* Mark the workaround in the code and documentation so it is never mistaken for the intended design.

**ADR record format** (store in `/docs/adr/`):

```markdown
# ADR-[YYYYMMDD]-[Feature]: [Title of Workaround]

* Status: Active (Workaround)
* Date: YYYY-MM-DD
* Owner: @<handle>
* Target Constraint: [Description of the failing primary tool/API]
* Options Considered: [Alternatives evaluated and why they were rejected]
* Adopted Solution: [Mechanism of the implemented fallback/bypass]
* Safeguards Implemented: [Backoff, circuit breaker, provenance tags]
* Compliance Review: [Approver name/role, date, scope of approval]
* Trade-Offs & Known Debt: [Performance, maintenance, or complexity cost]
* Rollback Plan: [How to disable the workaround and revert safely]
* Review Date (required): YYYY-MM-DD
* Deprecation Trigger: [Event that retires this workaround, e.g., vendor API update]
```

## Part 2: Escalation Protocol (When Engineering Bypasses Fail)

Enter this part if the bypass options are exhausted, the prototype fails, no compliant alternative exists, or the constraint is a policy-based hard limit. Steps may run in parallel where practical.

### Part 2, Step 1. Challenge the Requirement (Scope Reduction)

* **Critical question:** Does the end user genuinely require this exact technical mechanic, or only the underlying value?
* Temporarily simplify or eliminate the rigid specification.
* Define the **minimum viable outcome** the user or stakeholder agrees is acceptable, and deliver it with a simpler approach. Agree on what "good enough" means with the people who depend on it.

### Part 2, Step 2. Shift the Workload (Architectural Pivot)

Move execution to an environment that removes the bottleneck:

* **Compute-bound:** move heavy client-side computation to an asynchronous backend worker.
* **Latency- or timeout-bound:** move synchronous real-time requests to background processing with polling, webhooks, or push notifications.
* **Storage- or memory-bound:** shift from memory-heavy operations to stream processing or sharded data chunks.

### Part 2, Step 3. Human-in-the-Loop Fallback ("Mechanical Turk")

When full automation cannot be achieved reliably, protect the user experience with a human review path:

* Route failed or ambiguous tasks to an internal, secure review queue.
* Let an operator resolve edge cases, and log them for future automated refinement.
* **Safeguards:**
  * Role-based access controls and audit logs for the queue.
  * A defined SLA for review turnaround, with alerts for backlog.
  * **Data-privacy handling:** redact or restrict access to personal and sensitive data, apply the minimum-necessary principle, and set retention limits for items in the queue.
  * Training or written guidelines for operators, to keep decisions consistent.

### Part 2, Step 4. Negotiate the Blueprint (Stakeholder Alignment)

* Compile the evidence: engineering hours spent, methods attempted, and quantitative performance and error logs.
* Present the technical ceiling as an empirical constraint, not a development failure.
* Present options, with trade-offs for each: revised architecture, adjusted timeline, reduced scope, added budget, or an alternative definition of success.
* Obtain a recorded decision from the accountable stakeholder, then update the project plan.
