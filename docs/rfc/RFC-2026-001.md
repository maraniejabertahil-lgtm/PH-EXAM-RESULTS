# RFC-2026-001: System-Wide Phase 1 Ingestion, Parsing, and Validation Optimization

- **Owner:** Automated Pipeline Operations / Engineering
- **Original date:** 2026-11-03
- **Revision:** 1
- **Status:** Revised proposal — approved direction for staged technical implementation
- **Target:** `python-engine/`, `tools/`, `.github/workflows/`
- **Governing documents:** `Master_Technical_Blueprint.md`, `AI_BLUEPRINT.md`, `PROGRESS_TRACKER.md`, `IMPLEMENTATION_ROADMAP.md`, and `LIVE_ACCEPTANCE_TEST_REGISTER.md`

## 1. Executive decision

Adopt the performance and maintainability goals of the original RFC, but do not implement its unconditional four-layer replacement or broad system-wide migration.

The revised approach will:

1. Preserve the existing Python Engine architecture and extend its established modules.
2. Benchmark the current implementation before changing it.
3. Select acquisition methods according to the official source's permitted public access route.
4. Evaluate PyMuPDF against the existing parser using real representative documents and resolve its licensing implications before production adoption.
5. Strengthen independent validation and evidence without weakening Greenlight.
6. Remove unnecessary CI dependencies and enable dependency caching.
7. Pilot the optimized pipeline on the active PRC LEPT Secondary Phase 2 task.
8. Consider wider PRC reuse only after the pilot passes its accuracy, compliance, reliability, and performance gates.

This RFC does not authorize access-control circumvention, paid services, unverified publication, CSC-specific work, or a Phase 3 transition.

## 2. Problem statement and goals

The original proposal identifies avoidable cost in browser automation, page-by-page viewer capture, OCR installation, repeated dependency installation, and fragile parsing assumptions.

The objective is to reduce unnecessary acquisition and processing overhead while retaining exact official passer-name and sequence-number integrity.

### 2.1 Goals

- Reduce processing time and dependency overhead where measurements show a real improvement.
- Keep Python as the primary ingestion, extraction, validation, and dataset-generation language.
- Reuse existing modules rather than create a parallel engine.
- Preserve exact source names, sequence numbers, Unicode characters, and provenance.
- Keep Greenlight fail-closed and require a score of 100/100 for automatic publication.
- Preserve the last known-good public dataset after any failure.
- Keep all services and dependencies within the project's approved $0 operating constraint.
- Support multiple compliant official content formats without making PDF download mandatory.

### 2.2 Non-goals

- Replacing the repository architecture wholesale.
- Requiring a direct PDF download for every examination.
- Treating OCR as a default extraction method.
- Guaranteeing a complete GitHub Actions run under 60 seconds before benchmarks exist.
- Migrating every examination pipeline in one change.
- CSC-specific source discovery, acquisition, extraction, or testing; excluded by Owner decision D-003.
- Changing the Master Technical Blueprint or AI Blueprint through this RFC.

## 3. Governing constraints

The following constraints are mandatory and take precedence over performance targets:

1. **Official-first and content-first:** obtain publicly released passer names paired with their official sequence numbers from the most reliable compliant official source. A PDF is optional.
2. **Authorization:** use only publicly accessible and authorized source routes. Respect robots.txt, published terms, rate limits, and reasonable request pacing.
3. **No circumvention:** do not bypass CAPTCHA, sign-in, MFA, permissions, access controls, or technical barriers. Use the approved manual handoff when required.
4. **Fallback evidence:** record official attempts before any permitted third-party fallback. Fallback requires two independent sources with exact agreement on every sequence/name pair and announced count.
5. **No guessing:** never infer, invent, renumber, or silently repair missing records.
6. **Greenlight:** automatic publication requires 100/100 and every required integrity gate to pass.
7. **Preservation:** failed extraction or publication must not replace the last known-good dataset.
8. **Cost:** no paid service, subscription, API, or infrastructure may be introduced.
9. **Phase boundary:** complete the current Phase 2 real PRC batch task before expanding scope. Do not start Phase 3.
10. **Blueprint authority:** this RFC implements within the existing blueprint; it does not amend the blueprint.

## 4. Revised architecture

Do not introduce a second parallel `python-engine/core/` architecture. Extend the repository's existing module boundaries.

| Existing responsibility | Revised responsibility |
|---|---|
| Acquisition scripts and approved source adapters | Discover official content, record attempts and provenance, acquire only through permitted routes |
| `python-engine/extractor/` | Extract raw text/tables/records using a selected parser; preserve source order and raw values |
| `python-engine/processor/` | Normalize comparison values, validate sequence coverage and record integrity, calculate Greenlight |
| `python-engine/publisher/` | Generate dataset shards/manifests and perform the existing GitOps PR/CI/merge workflow |
| Shared evidence helpers, placed in the existing package structure where appropriate | Record acquisition, extraction, validation, and independent-review evidence |

A small shared interface may be introduced where duplication is demonstrated. New abstractions must not duplicate existing responsibilities or create a second route to publication.

### 4.1 Acquisition

The acquisition layer must support more than one source format, selected per examination:

- Official result article or result page.
- Officially exposed portal data or embedded dataset.
- Official CSV or other structured export.
- Official PDF where acquisition is authorized and technically available.
- Public preview UI or owner-reviewed manual handoff when direct acquisition is unavailable or not permitted.

Direct HTTP PDF acquisition is permitted only when the official source exposes an authorized public document route and the access conditions allow automated retrieval. The existence of a Google Drive preview link does not by itself authorize use of an undocumented download endpoint. Do not use private APIs or alternate endpoints to evade the visible access route.

For each attempt, record at minimum:

- Requested URL and timestamp.
- Retrieval method.
- HTTP status and content type, where applicable.
- Final URL and redirect host.
- Response size or visible page count, where available.
- Source fingerprint (SHA-256 when bytes are legitimately available).
- Outcome and concise failure reason.
- Whether a manual handoff was required.

Use bounded retries with backoff, request timeouts, response-size limits, host validation, and idempotent evidence writes.

### 4.2 Parser evaluation and selection

The current parser remains the baseline until a candidate proves better on representative source material.

Evaluate:
- Existing `pdfplumber` extraction.
- PyMuPDF native text and block/coordinate extraction.
- Other already-approved or permissively licensed alternatives only if the first two do not meet the measured requirements.

PyMuPDF is a candidate, not an unconditional production dependency. Before adoption:
1. Verify its current license and obligations from the official project documentation.
2. Assess compatibility with the repository's distribution and deployment model.
3. Record the decision and rationale.
4. Compare output integrity, layout handling, runtime, memory, and dependency footprint against the baseline.

Do not merge PyMuPDF into production requirements until this review is recorded. If its licensing obligations are unsuitable, retain or select a compatible alternative.

Parser requirements:
- Preserve raw extracted values and page/source locations.
- Preserve Unicode letters, combining marks, and legitimate name punctuation.
- Do not silently correct spelling or normalize published source text.
- Use normalization only for comparison and validation; retain the original source value for publication.
- Support layout-aware extraction where columns or reading order require it.
- Treat parser errors and incomplete page processing as failures, not partial success.
- Do not infer sequence numbers or fill gaps.

OCR is an optional fallback only when native text is unavailable or demonstrably unusable and the fallback is authorized and separately verified. OCR output is advisory until independently checked; OCR must not silently certify or repair records.

### 4.3 Validation and Greenlight

Strengthen the existing `processor/` validation path rather than create a duplicate validator.

Required gates include:
- Announced record count matches the extracted unique sequence count.
- Every expected sequence is present exactly once.
- Zero missing sequences.
- Zero duplicate sequence numbers.
- Zero conflicting sequence-to-name assignments.
- Zero blank names.
- Zero out-of-range sequence numbers.
- Zero unresolved parsing or layout anomalies.
- Required source provenance and acquisition evidence are present.
- Required independent verification evidence is present.
- Dataset and manifest fingerprints are internally consistent.

Additional rules:
- Preserve original source names exactly in the final record.
- Comparison normalization must not mutate source values.
- Duplicate names are review flags, not automatic proof of duplicate people. Two distinct candidates may share a name. A repeated name must be resolved according to the exam's source and record structure; never delete a candidate merely because the name matches.
- Any unexplained anomaly, incomplete capture, or unresolved verification issue blocks automatic publication.
- Greenlight remains fail-closed. No performance optimization may lower its required 100/100 threshold.

### 4.4 Evidence and independent verification

Evidence must distinguish machine-generated checks from human review.

Maintain three categories:

**A. Acquisition evidence**
- Official source URL and timestamp.
- Retrieval route and result.
- Final URL/host and response metadata.
- Source file or content fingerprint when available.
- Official-attempt history and fallback gate status.

**B. Extraction and validation evidence**
- Parser name/version and configuration.
- Input fingerprint and page/record counts.
- Extraction completion status.
- Missing, duplicate, conflicting, blank, out-of-range, and anomaly counts.
- Canonical record fingerprint and dataset fingerprints.
- Greenlight result and diagnostics.

**C. Independent verification evidence**
- First and last announced sequence/name anchors.
- Additional samples distributed across the document or data source.
- Page-boundary and layout-transition samples where relevant.
- Samples targeted at detected anomalies.
- Screenshots or source excerpts where the acquisition route supports them.
- Reviewer identity/role and review status where human review is required.

First/last screenshots are useful anchor evidence but cannot certify all records in a large batch. Screenshot hashes prove image integrity, not the correctness of every extracted record.

The pipeline must never set a human-review field to PASS solely because screenshots were captured, hashed, or OCR-processed. Machine verification and human visual review must remain separate statuses.

For a browser-only public preview, use ordinary visible UI navigation and capture stable rendered content. If a challenge or permission barrier appears, stop and use the approved manual handoff. For an authorized local PDF, do not launch a browser merely to extract native text.

## 5. CI and dependency optimization

The current Secondary workflow already uses `actions/setup-python@v6`; the revised optimization is to enable pip caching and point it at the correct dependency file.

Recommended pattern:

```yaml
- uses: actions/setup-python@v6
  with:
    python-version: "3.12"
    cache: "pip"
    cache-dependency-path: python-engine/requirements.txt
```

Apply only where appropriate:
- Install browser binaries and Playwright only for source routes that require browser rendering.
- Install Tesseract only in an explicitly selected OCR workflow.
- Avoid installing the same library redundantly through multiple commands.
- Keep dependencies pinned and review licenses before adoption.
- Separate baseline processing dependencies from optional browser/evidence dependencies.
- Preserve read-only workflow permissions until a specific, tested publication workflow requires additional permissions.
- Retain artifact evidence for failed as well as successful runs.

Do not impose a five-minute timeout until the optimized pilot has completed repeatedly within a measured safe margin. Set timeouts to prevent runaway jobs, not to conceal slow or incomplete processing.

## 6. Benchmark plan and performance acceptance

The original under-60-second target is retained as an optimization objective for the Python processing stage, not a guaranteed total GitHub Actions job duration.

Measure these components separately:
1. Runner startup and checkout.
2. Python setup and dependency cache restore/install.
3. Official source acquisition.
4. Extraction/parser execution.
5. Validation and Greenlight.
6. Dataset/shard/manifest generation.
7. GitOps PR and CI completion.
8. Total workflow duration.
9. Peak memory and artifact size.

### 6.1 Initial benchmark targets

| Component | Initial target | Acceptance rule |
|---|---:|---|
| Native-text parsing of a representative 1,000-page PDF | Under 10 seconds | Target only; must be measured on the actual runner and document |
| Validation of 50,000 records | Under 5 seconds | Target only; exact integrity must pass |
| Python processing after acquisition | Under 60 seconds | Target only; no integrity regression |
| Full GitHub Actions workflow | No fixed target initially | Establish baseline and repeatable measured target |
| Record integrity | 100% | Mandatory, not negotiable |
| Greenlight | 100/100 | Mandatory for automatic publication |
| Added service cost | $0 | Mandatory |

A benchmark is accepted only when:
- The exact input and its fingerprint are recorded.
- Baseline and candidate use the same input and runner class.
- At least three comparable runs are recorded for timing.
- The report includes median and worst observed time, not only the fastest run.
- Peak memory and dependency footprint are recorded.
- Every integrity and provenance gate passes.

A faster parser that drops, reorders, corrupts, or ambiguously joins records fails regardless of speed.

## 7. Staged implementation and migration plan

The implementation is deliberately narrow and gated.

### Stage 0 — Baseline and compliance inventory

- Re-read the governing tracker, blueprint, AI execution rules, roadmap, and acceptance register.
- Inventory the current extractor, processor, publisher, acquisition scripts, workflow dependencies, and tests.
- Capture baseline execution timings and current failure modes.
- Document the permitted official source route for the pilot.
- Review candidate parser licensing.
- Make no production parser replacement during this stage.

**Exit gate:** baseline and compliance evidence are recorded; the parser choice is documented.

### Stage 1 — Shared interfaces within the existing architecture

- Introduce only the minimum reusable acquisition/evidence interfaces needed to remove proven duplication.
- Preserve existing module ownership.
- Add bounded acquisition safeguards and structured provenance.
- Add regression tests before replacing any existing path.
- Keep the existing PDF parser available as a rollback path.

**Exit gate:** tests prove old behavior is preserved and the new interface fails closed on invalid or unauthorized acquisition.

### Stage 2 — Parser comparison and validation hardening

- Benchmark the existing parser and approved candidate on the same representative PRC input.
- Test multi-column and page-boundary layouts.
- Test Unicode names, punctuation, combining marks, repeated names, duplicate sequences, missing sequences, blanks, conflicts, and out-of-range records.
- Verify raw values are preserved and comparison normalization does not alter published names.
- Strengthen Greenlight and evidence separation.

**Exit gate:** exact record integrity and all required regression tests pass; parser licensing is resolved.

### Stage 3 — CI optimization

- Enable pip caching.
- Remove unnecessary OCR/browser installation from workflows that do not use those features.
- Split optional browser/OCR dependencies from baseline processing dependencies where this reduces installation overhead without breaking supported routes.
- Preserve logs and artifacts.
- Benchmark the resulting workflow.

**Exit gate:** measured improvement with no missing evidence, skipped checks, or reduced permissions safety.

### Stage 4 — PRC LEPT Secondary pilot (current Phase 2 task)

- Use the official PRC source and the permitted public acquisition route.
- Run acquisition, extraction, independent verification, Greenlight, dataset generation, GitOps PR, CI, and merge.
- Keep publication blocked unless all integrity, provenance, and evidence requirements pass.
- Preserve the existing public dataset if any step fails.
- Record all outcomes in the Live Acceptance Test Register.

**Exit gate:** the actual Phase 2 task is completed with evidence and the Owner confirms completion before its tracker checkbox is changed.

### Stage 5 — Controlled PRC reuse

Only after Stage 4 succeeds:
- Assess compatibility with the already-published PRC LEPT Elementary pipeline.
- Reuse shared components only where the source format and tests support it.
- Consider other PRC examination formats individually.
- Do not assume all PRC PDFs or result pages have the same layout.
- Do not begin CSC-specific work under this RFC.

**Exit gate:** each additional PRC format has its own representative input, source-access review, parser tests, and Greenlight evidence.

## 8. Testing requirements

Required automated regression coverage includes:

- Valid complete batch.
- Missing sequence.
- Duplicate sequence.
- Conflicting names for one sequence.
- Blank name.
- Out-of-range sequence.
- Repeated legitimate names.
- Unicode letters and combining marks.
- Apostrophes, periods, hyphens, parentheses, and supported punctuation.
- Multi-column and irregular reading order.
- Page-boundary records.
- Empty or image-only PDF.
- Malformed/truncated PDF.
- HTML/login/challenge response incorrectly presented as a PDF.
- Redirect to an unapproved host.
- Timeout, bounded retry exhaustion, and rate-limit response.
- Partial browser capture and unstable page text.
- Evidence hash mismatch.
- Incomplete artifact or manifest.
- Failed Greenlight preserving the previous dataset.
- GitOps failure leaving the known-good dataset untouched.

Tests must exercise both the selected primary route and supported fallback/manual route. A fallback must never bypass the same validation requirements.

## 9. Rollback and recovery

- Keep the existing parser and current working extraction route available until the replacement is proven.
- Keep changes isolated on a dedicated branch and use a pull request.
- Do not overwrite or delete existing published datasets during testing.
- Do not allow an incomplete candidate to reach the publication path.
- If parser comparison fails, revert to the existing parser without changing Greenlight.
- If acquisition is blocked, stop automated retrieval and use the approved manual handoff.
- If CI fails, preserve logs and artifacts, diagnose the cause, and repair the isolated branch.
- If publication fails, retain the last known-good dataset.

## 11. Completion criteria

RFC implementation is not complete merely because shared modules exist or a benchmark script runs.

The revised optimization is accepted only when:
- The Phase 2 Secondary batch completes the full real-world pipeline.
- All source-access and provenance conditions are met.
- Extraction and independent verification are complete.
- Greenlight scores 100/100.
- Dataset, shard, and manifest integrity checks pass.
- GitOps PR and required CI checks pass.
- Merge preserves the last known-good dataset until the new dataset is valid.
- Performance measurements show the actual improvement.
- The Live Acceptance Test Register records evidence.
- The Owner confirms the Phase 2 task is complete before the tracker is marked complete.
